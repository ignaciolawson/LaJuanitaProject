## Commands

Run from repo root unless noted.

```
npm install                # installs landing + platform (npm workspaces)
npm run dev:landing        # next dev
npm run dev:platform       # vite dev server
npm run build:landing
npm run build:platform

cd apps/landing && npm run lint       # eslint
cd apps/platform && npm run lint      # oxlint

cd apps/platform && npm test          # vitest, 358 cases, no backend needed
cd apps/platform && npx tsc -b        # typecheck. NOT `tsc --noEmit` — see below
cd apps/platform && npm run test:watch

cd apps/backend && mvn spring-boot:run
cd apps/backend && mvn test
cd apps/backend && mvn -Dtest=ClassName#methodName test   # single test

docker compose up -d       # Postgres on localhost:5432 (db/user/pass: la_juanita)
./scripts/pruebas-sql.sh   # the two SQL suites on throwaway databases
./scripts/backup.sh        # pg_dump with retention — see docs/operacion.md
```

**To see the platform running you need all three up**, in this order: `docker compose up -d`,
then `mvn spring-boot:run` in `apps/backend` (:8080), then `npm run dev:platform` (:5173).
The Vite dev server proxies `/api` to :8080, so the browser only ever talks to :5173.
Log in with **`admin@lajuanita.local` / `lajuanita2026`** — a development credential seeded by
`V3__usuario_admin_inicial.sql`, to be deactivated in a new migration before the real deploy.

**Use `mvn`, not `./mvnw`.** The wrapper tries to download its own Maven and fails on
this machine (`curl: Failed to fetch .../apache-maven-3.9.16-bin.zip`); a working Maven
3.9.14 is already on `PATH`. Java on `PATH` is JDK 25 while the pom targets 21 — that
compiles fine, it just isn't the mismatch it looks like. Docker Desktop is often not
running: `docker compose up -d` fails with a named-pipe error until you launch it.

**Database rule tests** — 230 cases (179 business-rule + 51 adversarial) covering every
rule the schema enforces (overlap, room×use matrix, premaster lock, state machines,
currency, discounts, deletion protection). They run against throwaway databases, never
the dev one. **Run them with `./scripts/pruebas-sql.sh`** — the nine-command procedure
that used to live in the file headers is gone, and so is the hand-maintained list of
migrations: **the script reads the migration directory**, so a new migration joins the
run on its own. That list was duplicated in both headers and went stale twice, at V4
and at V6. In Git Bash prefix `docker` calls with `MSYS_NO_PATHCONV=1` or it rewrites
`/tmp` into a Windows path — and never set that variable in a shell where you also run
`mvn`, because it breaks the Maven launcher's classpath.

**`mvn test` does not run them**, and that asymmetry is the point: the CHECKs, triggers
and EXCLUDEs are where this project put its business rules, and neither suite is part of
the Java build. The script exits non-zero when a case fails — the suites themselves print
a summary and exit 0 no matter what, which is why CI would have run them green forever.

Three rules those tests encode, each learned by getting it wrong: never hardcode IDs
(a rejected INSERT still consumes the identity value, so IDs stop being sequential);
a "should succeed" case must assert rows were actually affected — an UPDATE matching
nothing raises no error and passes vacuously; and **a "should fail" case must assert
the message**, which is the mirror of the second and cost the most. `probar` only
checks *that* a statement failed, so two cases sat green for a week over a trigger
that was crashing on an ambiguous column reference before it could apply its rule
(see `V16`). Use `probar_mensaje(nro, caso, fragmento, sentencia)` whenever the
expected rejection comes from a trigger.

**CI runs all four checkable things** (`.github/workflows/ci.yml`): `mvn test` against a
Postgres service — which also proves the eighteen migrations apply to an empty database, the
one thing nobody had verified before the audit — the SQL script, the two builds, the two
linters, and the platform's Vitest suite. The SQL script has a second mode for exactly
this: with `PGHOST` set it uses `psql` directly instead of `docker exec`, because in
Actions Postgres is a service, not a container you can exec into.

**Operations live in `docs/operacion.md`**: backup, **a restore that was actually
rehearsed**, and what to do when a migration fails. The restore rehearsal is worth knowing
about before you need it — it verified that the restored database keeps its *rules*, not
just its rows, that the real application boots against it, and **since the 2026-08-20
redo, that the uploaded files come back with it and that `archivo_path` finds them**. The one section left open
is deploy, which waits on the October hosting decision; it says so in its first paragraph
rather than inventing a procedure nobody ran.

## Architecture notes

**Data model — "usuario" is the root identity, not "alumno".** The original client-provided model treated `ALUMNO` (student) as the system's user, which breaks for one-off customers (someone who only rents the booth, buys gear, or sends a mastering job without ever enrolling). The corrected model: `usuario` is the single login identity; `alumno` and `profesor` are separate tables hanging off `usuario` via FK, not replacements for it. Transactional tables (`reserva`, `pago`, `venta_equipo`, `solicitud_reprogramacion`) key off `id_usuario`, never `id_alumno`. Full schema: `docs/db/la_juanita_schema.dbml.txt` (paste into dbdiagram.io to visualize).

**Two independent axes, not one `rol` column.** Permissions (what you may administer — this is what Spring Security reads) are separate from business relations (whether you have an `alumno` / `profesor` row — this is what builds the portal menu). Ghezz is `STAFF` *and* a `profesor` *and* can book a booth for himself, with no contradiction.

**There are four roles: `ADMIN` / `DIRECTIVO` / `STAFF` / `USUARIO`.** Not three. The plan of 2026-08-10 collapsed them to three; `docs/requirements/platform.md` §2.1 corrected that on 2026-08-11, because **Module 8 draws a real line between two kinds of administrator** (*"only directors and partners see the full dashboard; Micaela sees the basic financial summary"*) and three values can't express it. The commercial proposal also promises "four differentiated roles" — but **they are not these four: the count matches, the set doesn't.** It names *profesor* and *alumno*, which here are relations rather than roles, and never names `STAFF`. What the proposal commits to (four differentiated levels of access) is delivered; the literal list doesn't map one to one, and citing it as if it did is a weaker argument than Module 8 (DOC-10). **Six places** carry the four roles and must move together: the CHECK in `V1__baseline.sql`, the `Rol` enum in Java, the `Rol` type in TypeScript, `docs/db/la_juanita_schema.dbml.txt`, the two predicates in `apps/platform/src/layout/menu.ts`, and the `NOMBRE_DE_ROL` table in `UsuariosPagina.tsx`. Adding a role is a migration *plus* five file edits. The last two are typed `Rol[]` / `Record<Rol, string>` on purpose, so the compiler is the one that reminds you — the predicates used to be written by negation (`rol !== 'USUARIO'`), which let a hypothetical fifth role into the admin menu on its own and then get a 403 from the backend.

**Anyone can create their own account — student or not (P18, settled 2026-08-12).** `POST /api/auth/registro` is public and takes name, surname, email, phone, password. This is the clearest expression of the `usuario`-as-root decision: you need an account to see your bookings, and someone who rents a booth once never enrols. *Having an account* and *being a student* are separate — the `alumno` row is added later by staff. Micaela can also create accounts (for the ~80 students living in her Notion, and for people who sign up over WhatsApp): the system generates a temporary password she passes on via WhatsApp, and `usuario.debe_cambiar_password` forces a change on first login. No activation email — there is no mail infrastructure and there won't be soon.

**Registration deliberately tells you an email is already taken**, which undoes at signup the user-enumeration protection the login has. It's a considered trade-off, documented in `DatoDuplicadoException`: what leaks is "this address has an account at a music studio in Pilar", and the alternative strands anyone who registered months ago and forgot.

**`inscripcion` is where the course lives, and three of its rules are not in the schema** (built 2026-08-16, `com.lajuanita.backend.inscripcion`). The table has existed since `V1`; what the module added is the part a CHECK can't express:

- **The standard class count is filled in by the server, never by the form.** An alta that omits `clasesContratadas` gets 8 for DJ and 16 for Producción (§13, P34); `MENTORIA` has no standard and the alta rejects the request instead of guessing. The front carries the same table in `CLASES_ESTANDAR` **to display it**, not to decide it — if the two drift, Java wins.
- **Remaining classes are computed on every read**, by a native query against `reserva_participante` (no entity until Módulo 2). **That query is the same definition of "consumed class" as `V9` §5 and the two must move together**: if they drift, the screen says three classes remain and the database rejects the next one. The absent student *does* consume the class; a cancelled reservation or a cancelled participation does not.
- **The signature on a level downgrade is written by the server.** Only the reason comes from the request; the author comes from the token and the date from the clock. `Inscripcion.firmarBajaDeNivel` writes all three together because `V9` rejects the UPDATE if any is missing *or if the date is a previous downgrade's* — otherwise the second downgrade rides free on the first one's signature. The service's pre-check exists for the error message; `InscripcionTest` also drives a raw SQL UPDATE past it to prove the trigger is still what holds the rule.

**Módulo 2 closed on 2026-08-16** (`reserva`, `sala` packages): rooms and use types with the §2.6 matrix, the agenda by date range, reservations, participants and attendance, room blocking, and the usage report. Four decisions were settled that day — **classes are loaded by hand, one at a time** (P7: auto-generating the 8 weekly ones was the document's own recommendation and was rejected), **a class does not require an assigned teacher** (P37), DB-11 is done as an `@AssertTrue` on the reservation DTOs, and **the deposit trigger moved to Módulo 3** because it needs a `pago` row that no module can create yet.

**A `bloqueo_sala` row is a time slot that repeats on every day of the range, not one continuous interval.** That reading is what justifies the table having two dates *and* two times instead of two timestamps; `V6` wrote an EXCLUDE that read it the other way and `V7` had to undo it. The screen therefore says it out loud — *"09:00 a 13:00, **todos los días**"* — because here the wrong reading breaks nothing and is only discovered when someone schedules a class where it doesn't fit. Whole-day is the default and the hour fields don't appear until asked for. **The block is deleted, not cancelled**, and that's the one place in this schema where deleting is right: `V6` and `V7` banned deletion exactly where it matters (class history, money) and deliberately left this table out — a block is an operational note about the future.

**The usage report (`GET /api/reservas/uso`) starts from the room catalogue, not from the reservations.** A room with no use comes back at zero rather than not coming back: the zero is the number the report is opened for, and a missing row reads as lost data — the same reasoning as the student profile's placeholder blocks. Cancelled and rescheduled reservations are **counted separately and add no hours**: a room with twenty classes taught and one with twenty cancelled were not used the same way, and merging them erases the only thing the report is for. It aggregates in SQL rather than in Java — a year's worth of rows is what Módulo 8 will ask for — and its date cap is a year rather than the agenda's 62 days, because what bounds the agenda is the size of the response and here the response is three rooms whatever the period.

**Hibernate's write ordering bit twice more here, and the two halves complete the pattern:** `INSERT`s go before `UPDATE`s (already known — `ReservaService`), and **`DELETE`s go last, after the `INSERT`s** (new). Cancelling a class and blocking the room in one transaction was rejected because of the class just cancelled; unblocking a room and loading the waiting class in one transaction was rejected because of the block just deleted. Both times the trigger reads SQL, not the session. `BloqueoSalaService` flushes before the insert and after the delete. **The rule to carry: any operation whose rule lives in a trigger must flush pending work first — the trigger cannot see the session.**

**`@Column(insertable = false)` is not enough to return a database DEFAULT.** Hibernate never re-reads the column after the INSERT, so the row it hands back has `null` there. `BloqueoSala.fechaRegistro` needs `@Generated(event = EventType.INSERT)` because the alta echoes the created row and the screen shows when it was loaded. The other entities with a creation stamp use the same bare `insertable = false` and are **not** broken — none of them exposes it in a DTO, which is why it never showed up. Adding one to a DTO means adding the annotation. `VentaEquipo`, `SolicitudReserva` and `Notificacion` all needed it for the same reason.

**Two Hibernate write-ordering traps, both found by tests, both the same root cause — the ORM decides *when* the database gets to enforce a rule:**

- **Hibernate flushes INSERTs before UPDATEs.** Creating a rescheduled class inserted the new `reserva` while the original still counted as occupying its slot, and the EXCLUDE rejected it. Invisible when moving a class to another week; fatal when **shifting it by an hour**, which is the common case. `ReservaService` calls `flush()` after marking the original REPROGRAMADA and before inserting the replacement.
- **A native query flushes the whole session; a JPQL one does not.** `contarClasesConsumidas` was native, so it incidentally flushed pending `Inscripcion` updates and let the partial unique index reject a conflicting reactivation *during the request*. Converting it to JPQL silently turned that 409 into a 200. The fix was `InscripcionService.empujarALaBase()`, not reverting — **don't let a rule's enforcement depend on the side effect of an unrelated query.**

**A screen that can't be finished says so instead of omitting the part it lacks.** Same reasoning as `menu.ts`'s `disponible: false`: a missing block reads as *the system lost the data*, a labelled one reads as *not built yet*. Don't "clean up" those placeholders — deleting them makes the screen look complete when it isn't. **The student profile was the worked example and no longer has one**: it needed six blocks and could build two, and the other four arrived with the modules that named them — the last two on 2026-08-19 with Módulo 5. **When the module does arrive, the placeholder is replaced by the path, not deleted**: `MisCursosPagina`'s materials block now links to `/mis-materiales` under the same heading, because whoever once read that notice still looks for their materials there. Each of those placeholders also had a test asserting the notice, and that test is what tells you, on the day you build the module, that there is a sign left to take down.

**`npx tsc --noEmit` in `apps/platform` typechecks nothing.** The root `tsconfig.json` is a solution file — `"files": []` plus two references — so without `-b` there is no input and it exits 0 on a project full of type errors. **Use `npx tsc -b`**, which is what `npm run build:platform` runs; it was the build, not the typecheck, that caught a DTO field missing from every test fixture. A green `tsc --noEmit` here means nothing was checked.

**The front suite's timeouts are configured on purpose, and that is what makes a red run mean something** (2026-08-30, `mejoras.md` §9.6). It used to fail 1 run in 10 with nobody able to catch which test. It was never a test: it was two ceilings, both hit only under load — Testing Library's `asyncUtilTimeout` (1000 ms by default) against the `setTimeout(cargar, 250)` that **ten listing screens** share, and vitest's `testTimeout` (5 s) against `userEvent` filling a form. They now live in `src/pruebas/preparar.ts` (`configure({ asyncUtilTimeout: 5000 })`) and `vite.config.ts` (`testTimeout: 20_000`), and **the async ceiling must stay well below the test one**: if they matched, an element that never appears would eat the whole test timeout and the report would say *"Test timed out"* instead of *"Unable to find role=button name=Anular"* with the DOM printed beside it.

Two things this cost, worth not re-learning:

- **Repeating a suite proves nothing if you don't reproduce the conditions.** Eight consecutive green runs looked like the problem was gone; they only proved the machine was idle — those runs took 59–91 s against the 232 s of the run that had failed. With `mvn test` running alongside and `--maxWorkers=16`, it fell in 4 of 5 runs.
- **The redesign will break tests on purpose** — cases ask for visible text because they test product decisions, not pixels. Update the case; never dodge with `data-testid` and never weaken the assertion.

**A bug that looked intermittent for three days was in the path that doesn't fail** (`mejoras.md` §8.1). `FormularioParticipante`'s submit reset `enviando` only in the `catch`; the happy path relied on `setAbierto(false)` unmounting the component, and it doesn't — the component stays mounted and only changes what it renders, so the flag survived and the button stayed "Anotando…" forever. It looked like a hung request because **the first attempt always works**: it only shows when you reopen the form, i.e. when adding the *second* student to a group class. The four existing cases each added one participant, which is exactly why the suite never saw it. **Before waiting for a reproduction, read the path that succeeds.**

**Filtering students by discipline reads `inscripcion`, and three details decide the result** (settled with Ignacio 2026-08-16; the reasoning is in `docs/sistema-gestion-plan.md` §6d):

- **`EXISTS`, not `JOIN`** — a student can have several inscriptions, and a join repeats them once per course, which makes the page total lie.
- **One subquery, not one per filter.** Discipline and level must be satisfied by the *same* inscription: someone doing DJ inicial and producción avanzada is not doing DJ avanzado, and two separate `EXISTS` would return them anyway. Pinned by `disciplina_y_nivel_juntos_exigen_la_misma_inscripcion`.
- **Only `EstadoInscripcion.VIGENTES` (`ACTIVA` + `PAUSADA`) count.** The student list is the day-to-day tool: filtering "DJ" means who *is doing* DJ, not who finished it last year. `PAUSADA` counts because a paused course still has classes owed — hiding that student hides them from exactly the person who should chase them. The historical question is the Inscripciones screen's, which filters by state explicitly. `AlumnoResumen.disciplinas` uses the same set, so the list shows what it filtered by.

**`GET /api/profesores` exists only because the inscription screen needs it.** It is read-only and stays that way for now: a `profesor` row is created by giving the relation to a `usuario`, and that screen arrives with Módulo 2 along with the teacher's agenda. **It does not paginate, and that's a decision** — every other listing paginates because the business grows it (80 students today, more next year); this one is bounded by the studio's payroll and feeds a `<select>`, and paginating a picker makes it worse. If it ever gets uncomfortable, the fix is to make it a search like the student one, not to paginate it. It defaults to active teachers only, because offering someone who no longer teaches in a new inscription's picker is a load error worth not offering.

`SolicitudInvalidaException` moved from `alumno` to `usuario` when this module became its second user — it sits with `RecursoNoEncontradoException` and `DatoDuplicadoException` now. `Autoridades.idDe(Authentication)` came out of `UsuarioController` the same way (ARQ-06 again).

**Portal menu is three rules, not one.** Sections tied to a *relation* (Mis Cursos, Mis Alumnos, Subir Material) render only when the relation exists. Sections tied to a *service anyone can buy* (Reservar cabina, Mix & Mastering, Mis Pagos) always render — gate those on existing rows and a user who never booked can never make a first booking. Administration sections render by `rol`. All three are driven off `GET /api/me` (user + role + which relations exist); never hardcode the menu. The rules live in one file, `apps/platform/src/layout/menu.ts`.

That file also exports the **two role predicates the whole SPA shares**: `puedeAdministrar` (who sees the admin screens — gates the menu group *and* the `/admin/*` routes, so a visible section can never be a route that rejects you) and `puedeOperar` (who may write — ADMIN·STAFF, mirroring `@PuedeOperar`). `DIRECTIVO` sees every admin screen and gets no write buttons; before that, a partner would fill in "Nuevo alumno" and get *"No tenés permiso para hacer esto."* **Neither predicate authorizes anything** — the backend re-reads the role from the database on every request. Deleting them would open no hole, it would just go back to lying to the user. Add a screen, use them; don't write `rol === …` loose in a component.

**Login (built 2026-08-11).** `POST /api/auth/login` → BCrypt check → HMAC-signed JWT (8h, `sub` = user id, claim `rol`). **Nothing trusts that claim**: every authenticated request re-reads the user from the database (see the authorization note below), so a role change or a deactivation takes effect immediately. Signing and verification are Spring Security's own (`starter-security-oauth2-resource-server`) — there is no hand-written auth filter, and there shouldn't be. The front stores the token in `localStorage` and sends it as `Authorization: Bearer`; in dev the Vite proxy forwards `/api` to `:8080`, so CORS is not exercised locally even though the backend configures it.

Things worth not re-learning, most found by auditing the first version:

- **`NimbusJwtEncoder` defaults to RS256** and fails with *"Failed to select a JWK signing key"* unless you pass `JwsHeader.with(MacAlgorithm.HS256)` — the symmetric key alone is not enough.
- **Spring's default JWT validator does not require `exp`** — it only checks it when present, so a token without one never expires. `SeguridadConfig` adds validators requiring `exp` *and* `iss`.
- **All three login failures (unknown email, wrong password, deactivated user) return the identical 401 body** on purpose — *and take the same time*. When the email doesn't exist the code still runs a BCrypt comparison against a decoy hash; without it the response came back in ~10 ms instead of ~88 ms and that gap alone told an attacker which emails have accounts. Don't "optimise away" that seemingly useless comparison, and don't differentiate the messages.
- **`/error` must stay `permitAll`.** It is Spring's internal error forward, not an endpoint. Left authenticated, every error on a public endpoint comes back as an empty 401 — a malformed login body returned 401 instead of 400, hiding the real failure from the front end.
- **`@EnableMethodSecurity` is on.** Without it a `@PreAuthorize` compiles and silently does nothing, which is worse than having no annotation at all.
- **Spring Security 7 adds a `FactorGrantedAuthority` (`FACTOR_BEARER`)** alongside your own authorities. Assert `contains("ROLE_X")`, never `containsExactly`.
- **The JWT signing secret is committed** in `application.properties` so a fresh clone runs. Anyone who reads it can forge an ADMIN token, so set `JWT_SECRET` — to a *new* value — anywhere reachable from outside. **The lock fails closed**: signing with the committed secret aborts startup unless `lajuanita.jwt.permitir-secreto-de-desarrollo=true` is present in `application.properties`, the one line a deploy doesn't copy. It used to trigger only on an active `prod` profile, which was operationally empty — nothing in this repo activates a profile and the planned VPS deploy uses none, so a `docker compose up` with no env vars booted and signed with the public key, leaving one WARN line among hundreds. A lock against forgetting can't require having configured something else.
- **A null parameter in a JPQL `LIKE` blows up on Postgres** with `function lower(bytea) does not exist` — with no value, the driver can't infer the type and binds it as binary. Never pass null: `Busqueda.patron()` returns `"%"` for "match everything", and also escapes `%` and `_` so searching for "100%" works.
- **Never edit an applied migration — not even to add a comment.** Flyway checksums each file and refuses to start on a mismatch. This was learned by adding one explanatory comment to `V3` and watching the app die with *"Migration checksum mismatch for migration version 3"*.
- **A check-then-insert is not a uniqueness guarantee.** `UsuarioService` looks for a duplicate email before inserting, but another transaction can slip in between; six concurrent registrations of the same address produced four 500s. A double-click on the signup button is enough. The database's unique index is the real authority, so `ManejadorDeErrores` translates `DataIntegrityViolationException` into the same 409 the pre-check would have returned.
- **`spring.mvc.problemdetails.enabled=true` needs `@Order(HIGHEST_PRECEDENCE)` on our own advice.** Spring registers its own `@ControllerAdvice` above un-ordered ones and takes over `MethodArgumentNotValidException`, so the 400 kept arriving but lost the `errores` map the forms use to flag the offending field.
- **Spring Security's default 401 has an empty body.** `RespuestaDeNoAutenticado` supplies a ProblemDetail so the front end has a message to show and every error in the API has one shape.

**Authorization resolves against the database on every request, never against the token's claims** (`AutenticacionDesdeBase`). The `rol` claim inside the JWT is informational only — it authorises nothing. This costs one SELECT per authenticated request and buys the property the system documents everywhere else: **`usuario.activo = FALSE` removes someone immediately**, and a role change lands on the next request. The first version read the claim, and an audit measured the consequences on the running API: a deactivated STAFF kept listing students and *created a row*, a demoted ADMIN kept operating as ADMIN, and someone holding an unchanged temporary password kept working through the API because that block lived only in the front end. All three were the same bug. `CredencialVigenteTest` pins all three.

A user who still owes a password change gets the single authority `ROLE_PASSWORD_PENDIENTE` instead of their role: enough to reach `/api/me` and `/api/me/password` (both only require authentication) and nothing else, so the block cannot be bypassed by calling the API directly.

**Authorization by role exists as of 2026-08-12** and lives in two meta-annotations, `@PuedeLeerAdministracion` (ADMIN·DIRECTIVO·STAFF) and `@PuedeOperar` (ADMIN·STAFF). Beyond the role, `UsuarioService` also checks *who you are operating on*: **only an ADMIN may edit or deactivate an account that has an administrative role**, and **nobody may remove themselves from the system** — neither by deactivating their own account nor by changing their own role (the second door was open until 2026-08-14; the lone ADMIN could set itself to `USUARIO`, get a 200, and be locked out on the next request). Those two guards together hold the invariant *at least one active ADMIN always remains*, with no row counting: you can demote or deactivate someone else, never yourself. Without that, a STAFF could lock out the ADMIN — measured, not hypothetical — and since only ADMIN grants roles, that was enough to leave the system with nobody able to administer it. Keeping the rule in two places rather than scattered `@PreAuthorize` strings is what makes the four-role model enforceable: **`DIRECTIVO` reads everything and writes nothing**, and `PermisosPorRolTest` fails if anyone "fixes" that by adding DIRECTIVO to `@PuedeOperar`. Only ADMIN may grant roles — a STAFF alta that asks for `rol: ADMIN` silently gets `USUARIO`.

**The auth perimeter exists as of 2026-08-14** (SEC-02/03/08). Three things that weren't there and are easy to undo by accident:

- **Rate limiting** is split on purpose. Per-IP lives in `FiltroDeFrecuencia`, which runs *before* Spring Security's chain (`@Order(SecurityFilterProperties.DEFAULT_FILTER_ORDER - 1)` — that constant moved out of `SecurityProperties` in Boot 4.1). Per-email lives in `SesionService`, because the email is in the request body and reading a body from a filter means wrapping the request for nothing. A successful login clears the email counter. **`mvn test` disables only the per-IP limit**, from the surefire config in the pom — the suite is one machine doing hundreds of logins against 127.0.0.1, which is indistinguishable from an attack. Don't "fix" that by adding `src/test/resources/application.properties`: a file with that name *shadows* the main one instead of extending it, and takes the database config with it.
- **`RegistroDeEventos` is the only place in the backend that reads the request context implicitly** (`RequestContextHolder`, to get the IP). That's deliberate and concentrated in one method, so six services don't have to carry an `HttpServletRequest` they need for nothing else. Behind the planned HTTPS proxy it will log the proxy's IP until `server.forward-headers-strategy` is set — that's part of putting the proxy up.
- **A password reset exists**: `POST /api/usuarios/{id}/password-temporal`. It must keep going through `verificarQuePuedeTocarEstaCuenta` — without it a STAFF resets an ADMIN's password and owns the system, which is the 12/08 hole reopened through a new door. `PermisosPorRolTest` pins it. And the temporary password now expires (7 days, `lajuanita.password-temporal.vigencia`): `debe_cambiar_password` and `password_temporal_desde` are one fact in two columns and the database refuses to let them disagree (`usuario_password_temporal_coherente`, V8), so write them only through `Usuario.marcarPasswordTemporal` / `marcarPasswordElegida`.

**Naming: the domain is in Spanish, the framework's own vocabulary is in English.** This convention was followed from the first commit and written down only on 2026-08-15 (ARQ-08) — it had never caused a mapping bug, but every new file made you look around and guess, and three times the guess came out differently.

| Layer | Language | Examples |
|---|---|---|
| Java package names for technical layers | English, the conventional short word | `auth`, `config`, `web`, `dto` |
| Java package names for the domain | Spanish | `usuario`, `alumno`, `profesor` |
| **Everything else in Java** — classes, methods, fields, DTO components | **Spanish**, including inside the technical packages | `SeguridadConfig`, `AutenticacionDesdeBase`, `ManejadorDeErrores`, `LimitadorDeIntentos`, `Autoridades`, `SesionService` |
| Front — files and symbols | Spanish | `contexto.ts`, `credencial.ts`, `cliente.ts`, `menu.ts`, `paginas/`, `componentes/`, `RutaProtegida.tsx` |
| Front — names the framework imposes | English, unavoidable | `App.tsx`, `main.tsx` |
| Front — types mirroring a Java record | **The Java record's name, whatever language that is** | `LoginResponse`, `RegistroRequest`, `AltaUsuario` |

**At the border, the API path wins.** `LoginRequest`, `LoginResponse`, `AuthController` and `MeController` are in English because the endpoints are `/api/auth/login` and `/api/me`: the class is named after the URL it serves. That's why `AuthController` has a `login()` and a `registro()` fifteen lines apart, and why `RegistroRequest` is Spanish while `LoginRequest` is not — `/api/auth/registro` is a Spanish path. It looks like an inconsistency and it is the rule.

**Don't rename what exists to match this.** `LoginRequest` has tests on it and a rename buys nothing; the table describes where a *new* file goes.

**Backend**: Spring Boot 4.1 / Java 21, Spring Data JPA, Spring Security (JWT), Bean Validation, Lombok. `spring.jpa.hibernate.ddl-auto=validate` — no auto-DDL, ever. Schema lives in Flyway migrations under `src/main/resources/db/migration`: `V1__baseline.sql` (22 tables), `V2__datos_iniciales.sql` (rooms + the room×use matrix), `V3__usuario_admin_inicial.sql` (dev admin), `V4__separar_nombre_apellido.sql`, `V5__cambio_de_password_obligatorio.sql`, `V6__integridad_auditoria.sql`, `V7__auditoria_historial_y_bloqueos.sql`, `V8__vencimiento_password_temporal.sql`, `V9__reglas_cerradas_en_la_seccion_13.sql`, `V10__sena_obligatoria.sql`, `V11__la_sena_se_devuelve.sql`, `V12__la_sena_es_plata_que_entro.sql`, `V13__solicitudes_del_portal.sql`, `V14__notas_y_seguimiento.sql`, `V15__la_revision_de_mas_se_registra.sql`, `V16__el_candado_del_premaster_no_hablaba.sql`, `V17__avisos_automaticos.sql`, `V18__el_sello.sql` and `V19__pago_sin_cuenta_y_edicion_con_autor.sql`. **V6** closes 10 integrity holes found by attacking the running schema (12 CHECKs, 3 triggers, an EXCLUDE and a partial UNIQUE); the attacks and what was deliberately left open are written up in **`docs/db/auditoria-2026-08-12.md`**, its companion document. **V7** adds the rules the scope document declares *confirmed with the client* and the schema never tried to enforce: annulling a payment now demands author, date and reason (it was the only exception in the whole schema that demanded nothing); class history — `reserva` and `reserva_participante` — can't be deleted and can't have attendance edited without naming who did it; `venta_equipo` gets a load stamp. It also fixes the `bloqueo_sala` EXCLUDE, which read a blocking row as one continuous interval while both triggers read it as a time slot repeating every day of the range — so it rejected legitimate blocks. **V8** gives the temporary password a date so it can expire. **V9** writes the rules `platform.md` §13 unblocked — they were unwritable before because a decision was missing, not because they were hard: nobody in two rooms at once (a real EXCLUDE for the teacher, a trigger for the student, because the student lives in `reserva_participante` and the time lives in `reserva`), `egreso` and `venta_equipo` can now be annulled and therefore can no longer be deleted (the condition V6 §7 wrote down for itself), a level can't drop without author and reason, `sala.activa = FALSE` finally means something, and no inscription can consume more classes than it contracted. **V10** is the deposit and **V11** finishes it (see the deposit note above). **V13** is the portal's request table (see the Módulo 4 note below) and **V14** carries a single rule — the teacher's follow-up state seals its own "changed on" date. **V15** removes `V6` §3's ceiling on revisions because it made §9's own alert impossible to write, **V16** fixes `V6` §6's trigger, which crashed on an ambiguous column reference before reaching its own message (see the Módulo 6 note), and **V17** carries one rule — an automatic alert is written once per fact no matter how often the scheduler runs — as a nullable `clave_evento` plus a *partial* unique index on `(id_usuario_destino, clave_evento)`. **V18** carries the Módulo 7 rules `V1` left half-written (see the Módulo 7 note). Módulo 8 added no migration, which follows from what a dashboard is — it only reads. **`V19`** is the first migration of the improvement phase rather than of a module: it makes `pago.id_usuario` nullable behind `pago_pagador_identificado` (account **or** written name — the same two-path shape as `venta_comprador_identificado` and as `V10`'s deposit), and it lets a payment be edited as long as the author is named, reusing `V7`'s own `exigir_autor_de_la_edicion()` untouched. The two went in **one** migration on purpose: they touch the same table, so it is one review of `pago`'s rules instead of two. **`V20__el_buzon_de_solicitantes.sql`** is the inbox for the landing's forms (see the note below), and **`V21__los_comprobantes_de_un_pago.sql` is the last one (2026-08-30)** — a payment's receipts become a table of real files (see the note below). As of 2026-08-30 all twenty-one apply cleanly to an empty database and both SQL suites pass on the result (205/205 and 56/56) — and **CI proves that on every push**, which is what "applies cleanly to an empty database" needs to keep being true. ⚠️ **The next free migration is `V22`**, which is where deactivating the seeded dev admin goes.

**What `V19` cost outside the migration is the part worth carrying: five queries assumed every payment had an owner, and three of them failed silently.** The list was written down *before* coding (`docs/mejoras.md` §9.1) and every item on it was real. `PagoRepository.listar` and `porIdConDetalle` used `JOIN FETCH` — an INNER — so **a payment without an account vanished from the listing with no error and answered 404 by id**. Worse, two places grouped by the owner: `deudores` and the board's `conversion` both did `GROUP BY id_usuario`, and **a NULL collapses every ownerless row into a single group** — two different external debtors shown as one, with a total belonging to nobody. The alert scheduler had the same shape in its dedup key (`DEUDA:u=null:…` is identical for everyone), so the partial unique index of `V17` would have let **one alert stand for all of them**. Making a NOT NULL column nullable is never just the column: grep for every `JOIN` and every `GROUP BY` on it.

**A payment's receipts became a table on 2026-08-30 (`V21`), and the reason is the one the old column could not answer.** This is Módulo 3's oldest debt — receipt downloads, open since August, unblocked when Módulo 7 finally built §2.4's `StorageService`. What was there was worse than "the download is missing": **`pago.comprobante_path` was a text field somebody typed**, so the system displayed backing where none existed.

The business question was answered before any code (the fifth time that order paid off): *the hard rule of §6 is that receipts are never deleted, only marked invalid — so when the wrong file is marked, where does the right one go?* With a single column it has to overwrite the one that's there, **and overwriting erases the signature `V7` demanded** (who said it was wrong, and why). So the mechanism that exists to leave a trail becomes the one that destroys it. A payment now has many receipts: the wrong one stays listed as invalid with its signature and the right one is added beside it — the same criterion by which this schema deletes neither a payment, nor a class, nor a contract backing something published.

- **`V21` §3 is the half that nearly went missing**, and it is `V18` §1b's shape exactly: the table buys nothing if the row can be edited. Changing `archivo_path` is the overwritten column with extra steps, and setting `invalido` back to FALSE undoes a signed act with no trace. **From inside "it isn't deleted, it's marked" you cannot see the other half — that the mark isn't deleted either.**
- **The five old columns leave `pago` rather than staying alongside**, and **their values are not migrated**: they were hand-typed text, so copying them would fabricate backing that doesn't exist — the failure mode the restore rehearsal proved from the other side. The migration prints a NOTICE with the affected ids instead of discarding them silently.
- **Attaching is a second request, and that changed two altas' responses.** A file doesn't travel inside JSON, so `POST /api/reservas` and the room-request approval now return **the id of the payment they created** (`ReservaCreada`, `AprobacionRealizada` — `ConversionRealizada`'s mould). Without it §9.9 collapses: the receipt is lost at the very moment it exists, which was that finding's whole argument. **A nullable field on `ReservaResumen` was rejected** — that record also draws the agenda, where it would always be null and read as "this reservation has no deposit".
- **The `Content-Type` comes from the file, not from a constant.** `ContratoController` always answers `application/pdf`, which held while the only file in the system was a scanned contract; **half the receipts are phone photos of a transfer**, and serving those as PDF hands the student a file nothing opens. `TipoDeArchivo.porClave` derives it from the key the system itself wrote.
- **The student downloads their own through `GET /api/me/comprobantes/{id}`**, not through the admin endpoint with a looser role: the owner's id comes from the token and someone else's answers "doesn't exist". That closes the last of the three things Módulo 4 stated on screen instead of omitting.
- **Editing a payment doesn't touch its backing.** The receipt left the correction form: it is a file with its own signature, not a field.

**And a Hibernate trap that cost two red cases**: hanging the receipt only off the owning side saves the row correctly, but **the `Pago` already in the session keeps showing the old list** — attaching and then re-reading the payment in the same transaction returned zero receipts. `Pago.agregarComprobante` sets both ends.

**The deposit rule (DB-04a) shipped on 2026-08-17 as `V10__sena_obligatoria.sql`** — a `CONSTRAINT TRIGGER … DEFERRABLE INITIALLY DEFERRED` on `reserva`. Ignacio's words: *"everything must be deposited up front, everything — except mix & mastering, which Ghezz decides case by case. The deposit is 50% of the total."*

- **"Everything" does not mean every `reserva` row needs its own payment.** No reservation exists without money behind it, and that money arrives by one of two routes: a `pago` pointing at the reservation (booth rental, set recording), **or the inscription that covers the class**, through `reserva_participante.id_inscripcion`. A student who paid the whole course up front does not owe a deposit per class — that would be charging twice. An **`ANULADO` payment does not count**, or annulling the deposit would leave the reservation with nothing behind it while the check said otherwise. The only exception is `MIX_MASTERING`, **by `tipo_uso.codigo` and never by row state** — a rule whose exceptions depend on state is the one nobody can later tell is being followed.
- **The 50% is checkable on an inscription and not yet on a reservation.** `inscripcion.precio_total` exists; **`reserva` has no price** — a rental's price comes from hours × a rate that isn't in the system yet (P13, still the one open question). The database requires *that a payment exists*, not *that it is half*; the screen enforces the half until `reserva` has a price.

**The rule reshaped the alta, and that's the part to not undo.** `AltaReservaRequest` now carries **its participants** and **its `sena`** (`AltaSenaRequest` → delegated to `PagoService.registrar` as `SENADO`), both optional in the DTO and neither optional in practice: the screen demands whichever the use type calls for, and the trigger rejects at COMMIT whatever is missing. Going back to "create the reservation empty, add people later" makes every class alta fail, because at COMMIT there is no inscription and no payment. The rental half was nearly missed: a booth rental has no inscription at all, so without `sena` in the same transaction `V10` made **half the calendar uncargable**.

**Two testing traps this created, both of which produce green suites over an unverified rule:**

- **A deferred trigger never fires in a transaction that rolls back.** `ReservaTest` is `@Transactional`, so `V10` was invisible to `mvn test`. Force it with `SET CONSTRAINTS reserva_con_sena IMMEDIATE` **after an `em.flush()`** — without the flush nothing is queued and the case passes having tested nothing.
- **The SQL suites have the mirror problem.** psql is in autocommit, so each `SELECT probar(...)` is its own transaction and the rejection lands *outside* `probar()`'s `EXCEPTION` block, taking the `INSERT INTO _resultado` down with it: the case doesn't fail, it **vanishes from the summary**. Measured — applying `V10` untouched dropped the adversarial suite from 50 cases to 44 and made **8 unrelated cases report "EL AGUJERO VOLVIO"**. Every reservation that survives to COMMIT now enters with its payment in a CTE, via a `sena()` helper each suite defines. The CTE keeps the reservation inside and the final `SELECT` outside on purpose, so `probar()`'s ROW_COUNT still comes from the reservation and the "an 'ANDA' must affect rows" guard survives.

**`V11` closed the hole `V10` left, and the rule is now whole (2026-08-17).** `V10` only guarded the reservation's *birth*; the invariant could be broken afterwards by annulling the payment. That needed a business answer, and Ignacio gave it: **if a reservation is cancelled, the deposit is refunded.** So the rule reads **every reservation that OCCUPIES ITS SLOT has money behind it**.

That looks like the state-dependent exception §13 rejected and isn't. §13 rejected *"unless it's empty"* and *"unless it's a class"* — categories invented for this one rule. `NOT IN ('CANCELADA','REPROGRAMADA')` is **`V1`'s canonical definition of "reservation that occupies the room"**, already used by the overlap EXCLUDE, both blocking triggers, `V9`'s "nobody in two rooms at once" and the usage report; this is its sixth use. And the proof it's the right reading: **under the other one, cancelling would be impossible** — the database would force "never refund", deciding a commercial policy the client decided the other way.

**Three triggers, three timings, and the timing is the design.** `INSERT` on `reserva` (`V10`) stays **deferred** — at insert time its participant doesn't exist yet. `UPDATE` on `pago` and `UPDATE` on `reserva` (both `V11`) are **immediate**: everything to look at already exists, and deferring them would turn the 409 carrying the trigger's text into a 500 at commit. The `reserva` one is the dodge — cancel, take the refund, un-cancel. The natural order is **cancel first, refund second**; the other way round the trigger says so. `ReservaService.cambiarEstado` gained an explicit `flush()` so the immediate trigger speaks inside the request rather than depending on some unrelated query's incidental flush.

**`V12` closed a hole `V10` shipped with, found the same day: a slot could be obtained by annotating a debt.** `V10` wrote the money condition as `estado_pago <> 'ANULADO'`, which reads as "the payment is still live" and isn't — `DEBE` and `VENCIDO` are also ≠ ANULADO and are precisely *money that was expected and never arrived*; `V11` inherited it when extracting the shared function. Verified against the running schema: a rental whose only `pago` was `DEBE` passed the check. The correct definition already existed and had a name — **`EstadoPago.ENTRARON` = (SENADO, PAGADO)** — used by `cajaPorMoneda`, `cobradoPorInscripcion` and `ventasConPago`; this was the fourth query needing that list and the only one that spelled it differently, against an explicit warning written in `ventasConPago`'s own comment. **The lesson worth keeping: a set of states written by what it excludes (`<> 'ANULADO'`) looks like the set written by what it includes, and isn't. When the set already has a name, use the name.**

**Módulo 4 closed on 2026-08-19** (`solicitud`, `notificacion`, `portal` packages; `V13`). It brought the system's **second axis of authorization**, and that is the part to carry forward — modules 5 and 6 need it too.

**The portal cannot create a `reserva`, and that is what shaped the whole module.** A reservation that occupies its slot needs money behind it in `SENADO`/`PAGADO` (`V10`–`V12`), and **a `USUARIO` has no way to put money into the system**: registering a payment is `@PuedeOperar`, all five payment methods are manual, and there is no gateway anywhere in scope. So the portal writes a **`solicitud_reserva`**, and the reservation is born when administration approves it and loads the deposit — in one transaction. **The module therefore starts with a migration, not a screen.**

- **A new table, not a generalization of `solicitud_reprogramacion`.** That one has `id_reserva NOT NULL` and a CHECK hanging off it; loosening the column turns each of its rules conditional, which is the state-dependent exception §13 rejected. And they are two lifecycles: one asks to **move** something that exists, the other to **create** something that doesn't.
- **What can be requested is catalogue data, not a list in code**: `tipo_uso.solicitable_por_usuario`, TRUE only for `ALQUILER_CABINA` and `GRABACION_SET`. It is **not** the negation of `es_clase` — M&M isn't a class either and still isn't requested here. Same reasoning as the room×use matrix being data.
- **Approving is charging.** The "yes" is a deposit form, not a button, and the request is approved **exactly as it was made** — there is no "approve but at 18:00". If the slot doesn't work it gets rejected with a reason and the person asks again, so what was approved is always something someone chose.
- **The requester is added as a participant of the reservation**, even though a rental isn't a class: they are occupying the room, it gives "my reservations" a single definition, and it makes `V9`'s "nobody in two rooms at once" cover them for free.
- **A resolved request is final** (`V13` §4, applied to both request tables). The dodge it closes: approve — which creates a reservation with its deposit — set the request back to PENDIENTE, approve again. Two reservations, two deposits, one of them unexplained.

**Authorization by identity is a `WHERE`, not an annotation** (`portal` package). Everything the portal reads hangs off `/api/me/**`; **no endpoint there takes an identity** — the id comes from the token's `sub`, and `PortalService` has no query capable of returning someone else's rows. There is deliberately no `@PuedeVerLoSuyo`: an annotation would suggest it authorizes something, and a scope that can be forgotten isn't a scope. A STAFF looking at someone else's record uses the administrative endpoint as always, so **no endpoint changes meaning depending on who calls it**. Someone else's row answers *"doesn't exist"*, never *"you can't"* — the second confirms the row exists, which is what an id-guesser wants to know. `PortalTest` is written almost entirely in pairs — one looks at their own, the other looks at the neighbour's through the same endpoint — because a missing identity filter is invisible: the screen works fine, and shows too much.

**"Mine" is defined once** (`ReservaRepository.deLaPersona`): you participate in it, or you paid for it. `reserva` has no owner column — participants live in `reserva_participante` and a rental may have none — and those are **the same two paths `V12` uses to find the money behind a reservation**, with the same state list, `EstadoPago.ENTRARON`. An annotated debt doesn't make a reservation yours, exactly as it doesn't back one.

**The portal's own projections are separate DTOs, and that is the point.** `ReservaDelPortal` doesn't carry the other participants (a group class has three students and each portal has no business naming the other two) nor `notas` (administration's own field); `ProgresoDelCurso` carries no price and no notes. Reusing `ReservaResumen` would have published both by accident the day someone adds an internal field to it. **The one thing that is shared is the account statement** — same DTO, same `DetalleDeCuenta` component — because there is nothing in it its owner can't see, and two readings of one balance is the easiest way to have them disagree.

**Availability is the agenda with the owners removed** (`GET /api/me/disponibilidad`): busy slots with a `RESERVADA`/`BLOQUEADA` reason and nothing else, because the full agenda says who has class with whom. **Blocks are expanded day by day** — `bloqueo_sala` is a time slot repeating on every day of the range, not one continuous interval, the same reading `V6` got wrong and `V7` had to undo.

**Notifications now have their first writer.** The table has existed since `V1` and nothing ever wrote to it; resolving a request does. It is an **inbox inside the system, not a delivery** — no mail infrastructure, no WhatsApp — so the content has to stand alone: a rejection's reason travels inside the text. **The 7-day debt alert is deliberately not here**: it runs with no request behind it, needs a scheduler and needs to decide what happens when it runs twice in a day. That's a different machine, not a missing notification type.

**`PUT /api/me/perfil` lets everyone edit their own name, surname and phone — and not their email.** The email is the login credential and there is no way to verify a new one (no mail infrastructure), so a typo locks someone out of their own account and nobody finds out until they try to log in. Changing it is an errand with administration, which already has the screen.

**Módulo 5 closed on 2026-08-19** (`docencia` package, `V14`, six screens). What it decided:

- **`/api/me/profesor/**` — the `/profesor` segment is the design decision.** One person can be a student *and* a teacher (Ghezz teaches and also rents a booth), so `/api/me/materiales` would be ambiguous: the ones I uploaded, or the ones I was given? The segment says **which relation I'm looking from**. The student's route doesn't carry it.
- **"My student" is two paths**, the same shape as "my reservation": an inscription assigned to me, **or** having been in a class I taught. The second one is **the substitute** — whoever covers someone else's class needs to leave that session's note, which is when it matters most.
- **That rule lives in Java, not in the database, deliberately** (reasoned in `V14`'s header): two paths written in SQL would be a second copy of a definition, and this project already pays that with `contarClasesConsumidas` vs `V9` §5. The consequence to keep in mind: **if a new endpoint forgets the check, nothing fails** — the screen works and shows too much. That's why `DocenciaTest` is written in pairs.
- **Being a teacher is a relation, not a role**: no `@PreAuthorize` can decide it, `DocenciaService` goes and looks for the row. An ADMIN without one doesn't get in.
- **Material travels as a link, not an uploaded file.** `material.archivo_path` waits for §2.4's `StorageService`; `V1`'s CHECK accepts either, so **the module ships whole without dragging the file infrastructure** — which Módulo 6 will have to build anyway to retain the premaster.
- **`V14` nearly duplicated a rule `V1` already had.** It was going to stop a note from hanging off another student's class; **`V1` §8.3 already does that**, and it surfaced because a test expected the new trigger's message and got the old one. **Before writing a rule into the database, look for it in `V1`** — its §8 is exactly "cross-table rules", the kind a new module is tempted to add.

**Closing the module found a hard rule that lived in no layer at all — and that is the lesson worth carrying, not the endpoint.** §8 reads *"sus notas privadas no las ven ni el alumno ni otros profesores. **Administración sí**"*. The first half was enforced twice over; **the second half had no endpoint, no screen and no test**, and the admin student profile still drew a *"todavía no disponible — Módulo 5"* placeholder for it. Nothing was failing: a rule nobody implements has nothing to fail. It surfaced only by re-reading §8 against what had been built. The fix is `GET /api/alumnos/{id}/notas` and `/materiales` (both `@PuedeLeerAdministracion`), which decided four things:

- **`DocenciaDelAlumnoService` is a separate class, not two more methods on `DocenciaService`.** That one has a property written in its header and held up by twenty cases: *everything* goes through `miDocencia` and `verificarQueEsMiAlumno`. These two methods must skip both — administration is nobody's teacher — and putting them there would turn that sentence into an almost-truth, which is the kind of comment nobody re-reads.
- **A new explicit query, not the old one with the teacher passed as `null`.** `NotaProfesorRepository`'s own comment had asked for exactly that the day before: a query that skips its filter when handed a null **can be called by accident from the teacher's portal and nobody notices** — the screen works and shows another teacher's notes. `todasSobreElAlumno` takes no teacher, so it cannot be misused that way.
- **`NotaDeAlumno` is a new DTO, not `NotaResumen` plus a field.** Two readings of the same row: the author already knows the note is theirs; on the profile, where three teachers' notes sit together, **the author is the data**. Same precedent as `ReservaDelPortal`.
- **It is read-only and stays that way.** Correcting a note belongs to its author — the signature *is* the data — and publishing material belongs to the teacher who uploaded it (§8: the student sees it only if the teacher enabled it). A PUT there would drain both rules of meaning.

Front-side decisions of the same module, all of them about what a screen can quietly say wrong:

- **The unmarked traffic light says "Sin marcar" and is grey.** `null` is not `VA_BIEN`: a green nobody set lies about a student nobody looked at, and finding those students is what the list is opened for. It lives in `componentes/Semaforo.tsx` because two screens draw it, and both have a case for the `null`.
- **A note travels with the id of the PARTICIPATION, and the dropdown hides that.** The teacher picks *"12/08 10:00 · Clase de DJ"*, never a number. Those classes come from the last 60 days of the agenda, **matched by `idUsuario`, not `idAlumno`** — a participation hangs off the user, and `AlumnoDelProfesor` carries both ids exactly so that cross can be made. A cancelled class is not offered: it wasn't taught, so there is nothing to note about it.
- **The student's own record comes from the Mis alumnos list, not from a per-student endpoint.** None is missing: the list already carries everything the header needs, and looking inside it has the property that **an id that isn't mine doesn't appear** — the same answer the backend gives from its side.
- **One destinatario control in Subir material.** "¿Para quién? → todos / un alumno". Two controls allow a contradictory request that the database rejects and that the form should never have let anyone write.
- **Students in the agenda are named, not linked.** The participation carries `idUsuario` and the profile opens by `idAlumno`; they are different things. You get there from Mis alumnos.

**Equipment sales closed Módulo 3 on 2026-08-17** (`com.lajuanita.backend.venta`, `/admin/ventas`). **It is not an inventory** — there is no own stock, sales go against Pioneer's (§1) — so there are no units to decrement and no catalogue to maintain: the row records an operation that already happened. Three things it decides:

- **The buyer may have no account**, which is why there are three columns for them. That's the flip side of `usuario`-as-root: *having an account* and *being a customer* are different, and plenty of buyers arrive through the Pioneer arrangement and never register. What **does** require an account is the payment — `pago.id_usuario` is `NOT NULL`, so there is nowhere to hang the money of someone who isn't in the system. The screen says so up front instead of sending a request the database rejects.
- **The payment is optional and rides in the same transaction** (same shape as the deposit, delegated to `PagoService.registrar`), because a sale and its collection are two facts — that's what `pago.id_venta_equipo` is for. The listing marks **what's missing, not what's normal**: an uncollected sale is flagged, a collected one carries no label.
- **`fecha_registro` needs `@Generated(event = EventType.INSERT)`** because the alta echoes the created row — the fifth instance of that trap, and the second entity to actually hit it.

**`egreso` and `venta_equipo` can be annulled as of 2026-08-17** (`PATCH /{id}/anulacion`, same shape and same `MotivoRequest` as `pago`; `PedirMotivo` moved out of `PagosPagina` into `componentes/` so all three read alike). Correcting a mis-entered row is annul-and-reload. **The expensive part was not the annulment, it was the caja:** `EgresoRepository.porMoneda` summed every expense in the period without looking at `anulado` — correct while nothing could be annulled, and silently wrong the moment something could, because annulling would stop removing the amount from the balance with no error anywhere. What made it easy to miss is that the income half already did it right (`EstadoPago.ENTRARON`), so the caja *looked* like it handled annulment. Pinned by `CajaTest.un_egreso_anulado_deja_de_estar_en_la_caja`. **A sale that still has a live payment cannot be annulled** — annul the payment first; cascading would let one person's signed action retire a row someone else signed, which is the same reasoning `V6` uses from the other side to protect the payment backing a released premaster.

**One thing Módulo 3 still leaves open on purpose:** a sale loaded without payment has no later way to be collected, since `/admin/pagos` only settles inscriptions and accepting the other destination means rebuilding that form (today it is student → their inscriptions). Deliberate: with annulment working, an uncollected sale is annulled and reloaded with its payment, and P33 already settled that this business collects up front and not in instalments.

Two traps worth carrying forward, both found by tests written against V7 rather than by reading it:

- **A CHECK that evaluates to NULL doesn't reject anything** — only FALSE does. `CHECK (... AND btrim(motivo) <> '')` let a row through with `motivo` NULL, because `btrim(NULL) <> ''` is NULL. Wrap the text in `coalesce(btrim(x), '')`.
- **A generated column is computed before the CHECKs run**, so an expression that throws (`daterange`/`tsrange` with the bounds inverted) pre-empts the constraint that would have explained the problem. `reserva_horas_validas` is unreachable for exactly this reason (DB-11). V7's generated columns return NULL instead of throwing, so V1's CHECKs stay the ones that speak.

**A new migration no longer requires editing the two SQL test headers.** It used to: they carried the list of migrations to apply, the list was duplicated, and it went stale twice — at V4 and at V6 — because a suite run against a schema that is no longer the project's proves nothing and doesn't warn. `scripts/pruebas-sql.sh` now reads the migration directory (`sort -V`, so `V10` doesn't land before `V2`), so the only thing a new migration still owes those files is a case for the rule it adds.

The dependency that carries the autoconfiguration is `org.springframework.boot:spring-boot-starter-flyway`. Same pattern elsewhere in this pom: it uses `spring-boot-starter-webmvc`, not `spring-boot-starter-web`. Don't port Spring Boot 3 dependency names from memory — check the 4.1 BOM.

**Business rules are enforced in the database, not only in services.** A Postgres `EXCLUDE` constraint makes overlapping `reserva` rows for the same `sala` impossible; a composite FK to `sala_tipo_uso` makes an unauthorized room/use combination impossible (no recording in Sala 1, no mentoring in the recording booth); triggers keep reservations and `bloqueo_sala` from overlapping; a partial unique index allows only one active `inscripcion` per discipline per student. Read the comments in `V1__baseline.sql` before changing any of them — each one encodes a decision from `docs/requirements/platform.md`. **`V6__integridad_auditoria.sql` is the other half of those rules** — money can't be deleted, a premaster can't be released without a payment behind it, state machines can't be walked backwards in two steps — and its rationale is in `docs/db/auditoria-2026-08-12.md`, including the list of rules deliberately left unimplemented.

Those rules only reach the user through `ManejadorDeErrores`. It maps constraint names to Spanish messages and turns a trigger's `RAISE EXCEPTION` (SQLSTATE `P0001`) into a 409 carrying the trigger's own text — without it, the 103 constraints all came out as *"Ese email o ese teléfono ya están registrados"* and the 10 triggers came out as **500**. When you add a rule to the database, add its message to that map.

**Módulo 6 (Mix & Mastering) closed on 2026-08-19** (`mastering` package, `V15`, `V16`, `/admin/mix-mastering` and `/mix-mastering`). **Almost all of its schema already existed** — the table, the premaster lock (`V1` §8.4), the forward-only state ladder (`V1` §8.5), and from `V6` both the protection of the payment backing a release (§6) and the ban on deleting rows (§7). What the module added is shape, and what it *found* is the part worth carrying:

- **`V6` §6's trigger was broken and no suite could tell.** `proteger_pago_de_premaster()` declared a variable named `id_pago` and compared it against the column of the same name; Postgres aborts with `column reference "id_pago" is ambiguous` **before reaching the RAISE that explains the rule**. So the message written for a human never fired; 42702 isn't P0001, so `ManejadorDeErrores` didn't translate it and the API answered **500 instead of 409** — the module's central rule looked like a broken system; and **the branch that should have allowed the operation** (another live payment still backs the release) blew up too, so it also rejected too much. `V16` fixes it by renaming the variable. The hole was never open — failing for the wrong reason still rejects — which is exactly why nothing surfaced.
- **The suites couldn't see it, and that is the general lesson.** `probar(...,'FALLA',...)` asserts *that* a statement fails, not *why*. Cases D02 and D03 sat green over a broken trigger. **A 'FALLA' case that doesn't check the message can't tell a working rule from a bug that crashes earlier** — the exact mirror of the rule already written for the other side (*an 'ANDA' case must assert rows were affected*). The adversarial suite gained `probar_mensaje(nro, caso, fragmento, sentencia)`; use it for any 'FALLA' case that targets a trigger.
- **`V15` reverses `V6` §3, and it is the first time an audit decision was undone.** §9's client-confirmed rule is *"alerta al superar las revisiones incluidas"*; `V6` §3 had added `CHECK (revisiones_realizadas <= revisiones_incluidas)`, which makes that alert impossible to write — **you cannot warn about something the database rejects**. The audit read the field as a counter that must not hold an impossible number; the business reads it as *"did this job go past what was sold?"*, and that question is unanswerable if the fact can't be recorded. Same precedent as P22: **a confirmed business rule beats an inference of the audit.** `trabajo_revisiones_no_negativas` stays — a negative count really is impossible.

What the module decided:

- **The hard rule has exactly one shape on screen, and the order is the decision.** You press *Entregar premaster*; with no payment the backend rejects and the screen shows **its words**; only then does *"Liberarlo igual, con motivo"* appear, and it costs a written sentence that gets signed. A "release without payment" checkbox sitting there from the start would make the rule a suggestion.
- **Cargar el link del premaster no es entregarlo.** Loading it is editing the file; releasing it is an act with its own rule — which is why there are five write endpoints and no generic PUT. Folded into one save, releasing a premaster would be one more checkbox in a form.
- **`TrabajoDelPortal` hides the premaster in the mapping, not in the screen.** A link hidden with an `if` in the front travels in the HTTP response anyway and is read with the browser's dev tools. Same reasoning that split `ReservaDelPortal` from `ReservaResumen`; here the second field that can't cross is `notasInternas`.
- **Charging can advance the state to `PAGADO`, under three conditions**: the job is already delivered (`ENTREGADO`/`DEBE`), it has an agreed price, and what was collected **in the job's own currency** covers it. A payment in pesos against a job priced in dollars is not converted — there is no exchange rate the system can invent, and adding them yields a number that is money in neither currency. Otherwise the state stays put and the board shows "cobrado X de Y".
- **The payment needs an account and the job doesn't.** `pago.id_usuario` is NOT NULL while half of M&M's clients are external with no account, so the charge form asks whose name the payment goes under instead of sending a request the database will reject — the same asymmetry equipment sales already had.
- **The client's portal screen is read-only**, decided rather than deferred: the real channel for requesting work is WhatsApp and most M&M clients never register. A request form would serve a minority and add a second lifecycle (like `solicitud_reserva`) to sustain it. `A_CONFIRMAR` already exists if it is ever built.
- **The audio never enters the system, so no `StorageService` was needed** (P23, §14) — it is still owed for Módulo 3's receipt downloads.

**Módulo 7 (Sello) closed on 2026-08-20** — the `sello` and `archivo` packages, `V18`, `/admin/sello` and `/admin/artistas`. Its eight open questions were answered first (`docs/requirements/platform.md` §15), which is the third time that order paid off. Asking them before writing code is what kept Módulo 6 from ever stalling, and it is now the third time it worked. What they settled:

- **The label contract is an uploaded FILE, not a link** (P38) — which the schema had assumed since `V1`: `contrato_sello.archivo_path` is `VARCHAR(500) NOT NULL` and the column is named *path*. So **Módulo 7 is the module that finally builds §2.4's `StorageService`, before the rest of the module**, and unlike M&M there was no case for dodging it: the hard rule is *"no release is published without its contract attached"*, and with a link that degrades to *"a link is filled in"* while someone else's Drive dies without warning. **⚠️ The consequence that is easiest to forget: `scripts/backup.sh` is `pg_dump` and nothing else.** With files on disk the database is backed up and the contracts are not, and that is discovered the day you need to restore — the files have to join the script *and* the restore has to be rehearsed again (`docs/operacion.md` §2). October's hosting decision now also needs persistent disk. It pays off twice, though: the same piece settles Módulo 3's open debt, the receipt downloads — **collected on 2026-08-30 with `V21`**, ten days later and without touching the piece.
- **Artists do not get logins** (P24). `artista.id_usuario` stays nullable and unused; no portal, no second identity axis. This answer alone makes Módulo 7 half the size it could have been.
- **Post-release tracking is in, entered by hand** (P25) — a "where it played" list per release, orderable by popularity. **No platform integrations of any kind**, which was asked in the same sentence so the answer could not mean two things. What still needs deciding before writing the table: what field *measures* popularity.
- **Retention = contracting a second service within 10 months of the first, counted from the first service's date** (P26), equipment sales excluded, and pausing-and-returning is not retention (it is the same inscription, so the definition excludes it without a special rule). It was the only Módulo 8 indicator that could not be built without a business definition. **What is still open is the denominator, and it has a trap worth knowing**: someone who signed up three months ago cannot count as lost — their 10-month window is still open — so putting them in the denominator makes the retention rate fall every time the studio gains students, i.e. **growth would read as decline**. The default is therefore *"those whose first service is more than 10 months old"*.

**The four cheap ratifications were answered the same day, and two of them change the work** (§15):

- **The release code is system-generated and old releases get loaded** — so the correlative must start **above the highest existing code, never from a row count**, and the column has to accept a hand-written code for a 2023 release. Generation is a convenience of the alta, not a constraint of the table.
- **A release CAN fall through after being confirmed**, which is **a migration inside Módulo 7**: today a release's state only moves forward (`V1` trigger) and there is no `CANCELADO`. The right shape is the one M&M already has — `CANCELADO` outside the ladder, reachable from anywhere, no way back — and cancelling becomes the only way to retire a release, since deleting isn't an option in this schema. *"It's rare"* argues for having it: the thing that happens once a year is exactly what nobody will be able to record the day it happens.
- **PDF and Excel export is in, with a high bar**: the export inherits the screen's filters (*"datos específicos"*, not a fixed dump), and every file carries a **traceability header** — which filters, when, who — because that file ends up in a partners' meeting where the only thing that matters is being able to say where each number came from. It needs a real xlsx (typed dates and amounts, not a CSV renamed) and two libraries, chosen when Módulo 8 is planned rather than mid-module. This is the answer that grows Módulo 8 the most.
- **One is still open and only because it was asked badly**: whether the pre-release alert has to *arrive* outside the system (mail/WhatsApp) or whether seeing it inside is enough. It blocks nothing — the in-system alert already writes itself — and the rephrased question is in the questions file.

**P25's sub-question was closed on the technical side, not the business one** (Ignacio: *"no te hagas mucho la cabeza"*): "where it played" is ordered by a **fixed hierarchy of appearance type** — radio > set > playlist > other — then by date, rather than by a hand-estimated reach number nobody could later defend. And the section is allowed to stay empty: *"si en el futuro no lo usan, que no lo usen y fue"*, so the screen has to read well with zero rows.

**What building Módulo 7 found is worth more than the module itself:**

- **The module's hard rule existed in no layer at all.** *"No release is published without its contract attached"* is in the scope as a client-confirmed rule, and there was no CHECK, no trigger, no service check and no screen for it. **A rule nobody implements has nothing to fail**, so no suite could warn — it surfaced by re-reading the scope against what was built, exactly like Módulo 5's §8 half and like `V16`. `V18` §2 writes it, with the registered exception the scope asks for in parentheses (motive in writing, signed by its author).
- **`CANCELADO` could be undone, in the label AND in Mix & Mastering.** Found by a case written expecting a cancelled release not to return to `A_CONFIRMAR`. The cause: putting `CANCELADO` *outside* the ladder drops it into the `ELSE 0`, so every other state ranks higher and leaving it never read as a step backwards. `V1` §8.5 wrote *"you can cancel from any state"* and nobody wrote the other half — **from inside that sentence you cannot see what's missing.** It is the two-step backward walk `V6` had already closed elsewhere, and `V18` §1b closes it for both tables.
- **No request DTO in this project used a primitive `boolean`, and now the reason is written down.** Jackson cannot fill a record's canonical constructor when the property is absent, so a form that omits a checkbox — the normal thing when it is false — gets a 400 that explains nothing. Optional booleans in request records are boxed.
- **Two existing tests corrected a change of mine.** Generalizing `prohibir_borrado_historico`'s message looked right — `V6` enumerated only two tables — but `V7`, `V9` and `V13` had been extending it, and two suites assert their own table's escape hatch. They were right on substance too: **the enumeration is the useful half of the message**, because whoever hits that error needs to know how *that* table is retired.
- **And the project's own rake, stepped on:** `V18` was edited after it had already been applied to the dev database, so Flyway's stored checksum no longer matched and the app would not boot. It was repaired without losing the demo data — the checksum algorithm was verified against untouched `V16` and `V17` before touching the row — but only because the migration was not yet committed. `V18` is immutable now.

Decisions the module made:

- **The hard rule has exactly one shape on screen, and the order is the decision** — the same as the premaster: press *Publicar*, the backend rejects, the screen shows **its words**, and only then does *"Publicarlo igual, con motivo"* appear.
- **A release is backed by its own contract OR by a general one of its artist.** Not an invented exception: `contrato_sello.id_release` has been nullable since `V1` with its own comment. Same two-path shape as `V10`'s deposit.
- **Publishing is not a value of the state dropdown.** Inside it, the module's hard rule would be crossed by picking an option from a list.
- **`aparicion_release`'s "popularity" order is a generated column**, so Módulo 8's "label activity" reads the same hierarchy instead of writing a second `CASE` — the debt this project already pays with `contarClasesConsumidas` vs `V9` §5.
- **Cancelling asks for confirmation and does NOT ask for a motive**, unlike publishing without a contract: `release` has no column to store one, and asking for a sentence that gets discarded is worse than not asking.

**The `StorageService` of §2.4 finally exists** (`com.lajuanita.backend.archivo`), after three modules dodged it. Two things it decides: **the stored name is chosen by the system, never by the uploader** (a client-supplied name can escape the folder, collide with another contract and overwrite it with neither row noticing, and carry characters Linux accepts and Windows doesn't — this project's exact crossing), and **the extension comes from the content**, read from the first bytes, because these files get served back. It writes **the file first and the row second**: an orphan file wastes space, while a row pointing at a missing file makes the system consider its own hard rule satisfied. Cleanup on rollback hangs off a `TransactionSynchronization`, not a `catch` — what can kill that transaction (the `V18` trigger at flush) happens *after* the method returns.

**⚠️ And it changed what "backup" means.** `scripts/backup.sh` was `pg_dump` and nothing else; with contracts on disk it now produces **two artifacts** (the dump and a tar of `lajuanita.archivos.raiz`), sharing one retention. The failure mode this avoids is among the worst available: the backup runs green daily, the database restores perfectly, and **every `contrato_sello` points at a PDF that does not exist** — nothing fails, and it is discovered the day someone opens a contract. **The restore rehearsal was redone with the files on 2026-08-20 and passed** (`docs/operacion.md` §2, now the current one): catalogue identical, the PDF back byte for byte, every row finding its file and every file its row, five rules rejecting **with their own message** — including the two the label added — and the closing step being the real application booted against the restored database *and* the restored files, serving the contract over the API. **The failure mode was also proved from the other side**: with the row intact and the file gone, the API answers *"No está el archivo pedido."* — the system only finds out when someone asks for it, which is why a database restored without its files looks perfectly healthy until the day someone opens a contract.

**Módulo 8 (Tablero de dirección) closed on 2026-08-20** — the `tablero` package, `/admin/tablero`, the Excel and PDF export. **It is the only module in the project that added no migration**, which follows from what it is: the board only reads. What it decided, and what it found:

- **`STAFF` sees less because it calls a DIFFERENT endpoint**, not because the same one returns less. §11 grants full access to ADMIN·DIRECTIVO and the basic financial summary to STAFF; doing that with one endpoint that answers differently by role breaks the property Módulo 4 imposed — **no endpoint changes meaning depending on who calls it** — and is unreadable in a test, since you need two users mounted to know what it returns. With two DTOs, a new indicator cannot leak to STAFF by accident: you would have to add it to the second one by hand.
- **Not every indicator belongs to the period, and the screen says so out loud.** Active students, live debt and retention are snapshots of today; income, occupancy, deliveries and releases are of the chosen period. Filtering a snapshot by the period answers a different question under the same title — looking at August would make March's debt disappear, which is exactly the money someone has to go collect. The exported file repeats that line inside every sheet, because whoever opens it three months later doesn't have the screen that explained it.
- **A payment's line of business comes from what it points at**, and for a reservation, from that reservation's **use type**. Without that cross, every deposit lands in one bucket and the board says the studio bills for renting what it charged for teaching. The definition lives once, in SQL.
- **The caja is not recomputed**: it comes from `PagoService.caja`, from Módulo 3. Rewriting that sum would have been this project's third copy of a definition and the worst of them — two screens showing different totals for the same month. A test compares both responses so the copy can't be introduced later.
- **Retention (P26) ratified its denominator** as §15 anticipated — only those whose 10-month window has closed. **But building it found a second trap that was written down nowhere, and it is worse than the one that was: the classes of a course are not contracted services.** A DJ inscription is eight reservations; counting them would make every student "retained" a week after starting and the rate would read near 100%. **Nobody would have questioned that number** — a 95% retention gets celebrated, not audited. A wrong indicator doesn't fail; it convinces.
- **With a zero denominator the rate is `null`, not zero** — in the JSON, on screen and in the spreadsheet. A 0% reads as "everyone left"; what's happening is that nobody's window has closed yet. It is the same distinction the Módulo 5 traffic light makes between "going well" and "unmarked", and it is exactly what the development database returns today.
- **"Zero, not empty" is held by the backend**, not the screen: the occupancy grid travels complete and always covers the studio's opening hours, stretching if something fell outside. In the front it would be a drawing detail that the end-of-project redesign loses.
- **One report assembly, two formats.** Excel and PDF read the same sheets of typed cells and neither decides what to show. Written separately, a new indicator would eventually land in only one and nobody would notice until two people compared their files in a meeting.
- **The traceability header repeats in every Excel sheet and in every PDF page footer.** The scenario: someone copies one sheet into another workbook and mails it, or prints a single page. That fragment has to be able to say where it came from.
- **OpenPDF, not iText**: iText 7 is AGPL and would force publishing the whole system or buying a licence. That is the main reason for the choice and it is written in the `pom`, not just in a commit.
- **A test from an earlier batch argued with a change of mine, and this time reverting it was right.** `menu.test.ts` asserted that STAFF didn't enter this screen and that its summary lived inside Pagos. It wasn't badly written — it was written on a different reading of the scope, from when Módulo 8 was still "trazo grueso". But §11 lists *"STAFF ve el resumen financiero básico"* among **Módulo 8's hard rules**: if that summary lived in Pagos it would be a Módulo 3 rule. The difference from the Módulo 7 case: that test defended a fact (which tables a message enumerates), this one defended an interpretation.
- **A Spring Data trap worth not re-learning**: a single-row query declared as `Object[]` still returns the list and casts it, so what arrives is an `Object[]` whose only element is *another* `Object[]`, and the `ClassCastException` surfaces only when you read the first column. Declare `List<Object[]>` and take the first.

This module also introduces **the system's third role axis**, `@PuedeVerElTableroCompleto` and its mirror `puedeVerElTableroCompleto` — the only place where the line separates two kinds of administrator rather than reading from writing, i.e. **the concrete reason this project has four roles and not three**. Until now it lived as a loose `u.rol === 'ADMIN' || …` inside the menu's switched-off placeholder item.

**The alert scheduler was built on 2026-08-20** (`V17`, `com.lajuanita.backend.aviso`) — the piece Módulo 4 (7-day debt), Módulo 6 (7-day unpaid delivery) and Módulo 7 (7 days before a release) each wrote down as *"belongs to whichever module builds automatic notifications"*. It was built **before** Módulo 7 rather than inside it, so the third alert is one more rule instead of infrastructure discovered mid-module — which is exactly what happened to the `StorageService` two modules running.

**What it found is the part to carry: `estado_pago = 'VENCIDO'` had existed since `V1` and no line of the system ever wrote it.** It is in the CHECK, it has its own index (`pago_deudores`), `EstadoPago` documents it as *"deuda que además pasó los 7 días (§6, alerta automática)"* and `ADEUDADOS` counts it — but the only way a row reached it was someone picking it by hand from the dropdown in `/admin/pagos`. **Nobody noticed because the debtors screen recomputes the age on the fly**: it looked right and the stored data wasn't. A 40-day debt and a 1-day debt were the same row to any query that didn't redo the arithmetic. Same shape as `V16`: no open hole, just a rule that existed in no layer and therefore had nothing to fail.

Four decisions the scheduler made:

- **The alerts go to administration, not to the person involved, and only to whoever can act** — ADMIN·STAFF, the `@PuedeOperar` set. `DIRECTIVO` reads everything and writes nothing, so *"go collect from this one"* would arrive for someone who cannot. For M&M it could not work any other way: half its clients are external with no account, and a notification needs a `usuario` destination.
- **The dedup key describes the FACT, never the run** (`DEUDA:u=42:ARS:desde=2026-08-01`). That buys both properties at once: running ten times today writes one alert, and if the debt is settled and returns three months later the `desde` differs, so the alert fires again. A per-run key would alert daily; a key with no date would never alert twice.
- **A partial unique index is what guarantees it, not the service's pre-check.** The service still filters first — to avoid attempting a hundred inserts that are already there — but between the query and the insert another run fits, which is the exact hole the duplicate-email pre-check had in `UsuarioService`. The index is **partial** because alerts written by a *person* carry no key and must not: two similar approved requests are two alerts and both have to arrive.
- **One alert per fact, not one per day.** The standing state is what `/admin/deudores` and the M&M board are for. A daily reminder of the same debt turns the inbox into noise, and then the alert that mattered goes unread.

**The third alert — Módulo 7's "one week to launch" — cost one query and a fifteen-line block**, because the machine was already there. The other two had spent months written down as *"belongs to whichever module builds automatic notifications"*. That is the whole argument for building shared infrastructure before the module that needs it rather than inside it, and it is exactly what did not happen to the `StorageService` twice running.

The front added no test cases, deliberately: `NotificacionesPagina` decides nothing from the alert's type — it renders title and body — which is why an automatic alert has to stand alone (*"Juan debe $50.000 desde hace 12 días"*, not *"tenés una deuda para revisar"*), and why administration sees them without touching the menu (`Notificaciones` has no predicate in `menu.ts`). The only front change is the TypeScript type, **which had also been missing `RESERVA_MOVIDA` since Módulo 5** — harmless precisely because nobody reads the type.

**The applicant inbox shipped on 2026-08-29** (`V20`, the `solicitante` package, `/admin/buzon`) — Fase 2.2 of `docs/mejoras.md`, hallazgo #7. The landing's four forms answer *"listo, lo recibimos"* without the request leaving the browser, which is why the landing cannot be published; this is the half that receives them. **The forms were wired on 2026-08-30**, so the circuit is closed end to end: `POST /api/solicitantes` from the landing, card in `/admin/buzon`, account created from there.

- **It is a TABLE, not a notification, and that is the design correction.** A notification is read and gone; an applicant is a card with a lifecycle (pending → converted → discarded), and what the inbox has to guarantee is that **the list of who nobody answered still exists**. Same pair the system already had: `solicitud_reserva` is the table with states and the notification is what *announces* it.
- **One inbox, not one per service.** The flows are identical until the last step — form → card → Micaela creates the account — and that last step is already built (`/admin/inscripciones`, `/admin/reservas`, `/admin/ventas`). The card only has to say **what they asked for**, which is what `interes` is; the screen turns it into the link to the right page. Equipment enquiries are in too (decided 2026-08-29): the fourth landing form existed and was equally mute. M&M stays out — it arrives by WhatsApp to Ghezz, the standing Módulo 6 decision.
- **`POST /api/solicitantes` is the first public write outside auth**, and the matcher is `HttpMethod.POST` on purpose: opening the route would publish `GET /api/solicitantes`, which is the inbox with everyone's phone and email. `SolicitanteTest` pins that with a case asking for the listing without a credential. It is also the fourth route in `FiltroDeFrecuencia` — worth attacking not for what it returns but for what it leaves, since `V20` rows cannot be deleted.
- **Converting has two paths and both end the same way.** The obvious one creates the account (delegating to `UsuarioService.altaPorAdministracion`, so the temporary password and `V8`'s expiry live in one place); the other — **the person already had an account** — is not a rare edge: a student of a year who asks for the booth from the landing arrives exactly like that. With one path that card jams against `usuario_email_unico` forever. `ConversionRealizada.passwordTemporal` is null on the second path and the screen says so, because a blank field there makes whoever is attending wait for a datum that does not exist.
- **No notification is written per incoming form, and that is decided rather than forgotten.** This is the only public writer in the system, so one alert per form is one per bot times every ADMIN and STAFF — the exact failure `AvisoService` documents. §9.4's own argument is that what prevents losing people is *the list*, not a sound. If announcing turns out to be needed, the right shape is a scheduler alert (*"3 cards unanswered for over 48 hours"*), one per fact.
- **Name and surname are two columns**, filled in as two fields by the form. It is `V4`'s lesson applied in time: there, one column had to be split by guessing where the name ended.

**"No puedo ese día" shipped on 2026-08-29** — `SolicitudReprogramacion` in the `solicitud` package, `/admin/reprogramaciones`, and the `PedirOtroDia` component. It closes Fase 2 of `docs/mejoras.md` and **adds no migration**: the table and its trigger have existed since `V1` and `V13`, with nobody writing to them. This is their first writer.

- **P9 was answered first** (`docs/requirements/platform.md` §16): **the teacher asks with the same button as the student.** Same endpoint, same component — only the screen it is entered from changes (*Mis reservas* vs *Mi agenda*). What that unlocks is not a screen but a datum: today the teacher tells Micaela over WhatsApp and **why a class moved is written down nowhere**, which is exactly what `solicitud_reprogramacion.motivo` has been there for since `V1`.
- **Approving moves the class IN PLACE, and that is the decision everything hangs on.** This system has two ways to move a reservation: `editar` (same row, another day — what the calendar does) and `alta` with `idReservaRecupera` (the original goes REPROGRAMADA and a replacement points at it — P2's *class recovery*, for the class that was **not given**). A reschedule request is the first: nobody missed anything, the class just moves. Picking the second would have created a money problem out of nothing — a REPROGRAMADA reservation stops owing a deposit (`V11`) and the new one owes one, so moving a booth rental would become charging again and refunding, two cash movements for one move. In place, **the money never notices**. `SolicitudReprogramacionTest` pins that by forcing `V10`'s deferred check after moving a rental: swap the approach and that case fails.
- **Here you do NOT approve "exactly as asked"** — the opposite of the room-request rule, and the table imposes it: `fecha_alternativa_solicitada` is an **optional** `DATE`, no time, no room. The difference is who can know what: whoever asks for a booth picks a free slot the portal shows them; whoever asks to move their class **cannot know** which room is free or which teacher it depends on. So approving is a form with the new slot, never a button — and the backend rejects approving with the same slot it already had, because a request marked approved with no movement notifies nobody and leaves the person waiting.
- **Approving sends no notification of its own.** `editar` already tells participants and teacher *from where to where*; a second alert for the same fact trains people to ignore them. Rejection does notify (`REPROGRAMACION_RECHAZADA`), with the reason inside — nothing moved, so without it the person is left waiting.
- **Three paths decide whose reservation it is**: being a participant, having paid it (the two `ReservaRepository.deLaPersona` already uses, the same two `V12` uses to find the money behind a reservation) **or being that class's teacher**. The third lives in `SolicitudReprogramacionService`, deliberately not added to `deLaPersona` — there it would make the classes he teaches show up among "his reservations" as if he were their client.
- **There is no "my change requests" screen, on purpose.** The request's state shows on the class itself, in both screens, through the same component: a request to move something is unreadable without the thing it wants to move.
- **`EstadoReprogramacion` has three values, not four.** The table has rejected CANCELADA since `V1`, so whoever changes their mind says so and administration rejects the request. Adding it is a migration for something the scope never asked for; the enum says so rather than leaving it looking like an oversight.

**Out of scope for now**: WhatsApp Business API integration — deliberately excluded from the initial commercial proposal, but flagged as the highest-value fast-follow after delivery (it targets the client's #1 pain point: manual WhatsApp replies for scheduling/payments).
